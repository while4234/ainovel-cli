# Project Artwork Workspace

AINovel stores cover, illustration, and character-portrait work under each
project's `output/artwork/` directory. The workspace is independent from the
Host creative workflow and does not acquire the normal-flow action lock.

## On-disk schema

`schema.json` identifies schema version 1. Every mutable or immutable record is
stored as a separate JSON file; image bytes are never embedded in JSON.

```text
output/artwork/
  schema.json
  drafts/<draft-id>.json
  prompts/<prompt-version-id>.json
  jobs/<job-id>.json
  assets/<asset-id>.json
  images/<asset-id>.(png|jpg|webp)
  apply/<target-id>.json
  staging/*.(pending|delete)
  journals/(finalize|apply|delete)-<id>.json
```

Drafts are mutable through an `expected_version` compare-and-swap. Prompt
versions, asset metadata, and installed image bytes are immutable. A generation
submission snapshots the prompt version, capability catalog version, requested
and resolved model IDs, size/aspect/resolution fields, response format,
normalized gateway endpoint, and deterministic asset ID. The gateway credential
is not copied into the project; the worker resolves the current global
credential only when it executes the queued job.

The normalized endpoint and provider-delivery details remain internal job
fields. Public job responses contain stable request metadata and safe error
codes only.

## Job lifecycle and one-shot execution

Jobs use exactly these states:

- `queued`: durable and safe to submit once.
- `running`: the one synchronous AI2API POST may have been submitted.
- `succeeded`: both immutable image bytes and asset metadata are durable.
- `failed`: a known failure occurred, such as a provider response, invalid
  image, or local persistence failure.
- `interrupted_unknown`: delivery may have occurred, so automatic retry is
  forbidden.

Only one `queued` or `running` image job may exist in a project. Generation
requires a client idempotency key. Repeating the same request returns the same
job and deterministic asset; reusing a key for another request is a conflict.
The worker performs at most one `POST /v1/images/generations` and requires one
`b64_json` result. It never follows or downloads a provider URL.

Generated bytes must decode completely as PNG, JPEG, or WebP, remain at or
below 25 MiB, and contain no more than 40 million pixels. Images are served only
by the project-scoped content and download handlers, which revalidate the
managed path, symlink containment, digest, MIME, and decoder result. The
artwork directory is not mounted as a static directory.

## Atomic finalization and recovery

Finalization writes and fsyncs an operation journal, writes and fsyncs a staging
image, atomically renames it to its deterministic final name, commits immutable
asset metadata, and only then marks the job `succeeded`. Repeating finalization
with the same bytes is idempotent.

Startup reconciliation runs before a project's artwork store is exposed:

- A finalization journal plus a matching staged or installed image is
  deterministically completed without another gateway request. This repairs
  the image/asset-before-job-terminal crash windows.
- A `running` job without matching local finalization evidence becomes
  `interrupted_unknown`; it is never submitted again.
- A `queued` job may be resumed and submitted once.
- Asset metadata without matching valid bytes is removed from the gallery and
  its succeeded job becomes `failed` with `asset_missing`.
- Image files not referenced by committed asset metadata are removed as
  orphans. Dangling apply pointers are removed.
- Apply and delete journals either complete or restore a consistent
  metadata/image pair. Applied assets are protected from deletion.

Original assets never change. Applying an asset updates only a small target
pointer under `apply/`. Reusing an asset creates an idempotent mutable draft
whose `prompt_source` is `reuse`; a later generated asset still records its
origin as `generation` and its `reused_from_asset_id` provenance.

## Project HTTP API

All workspace routes are under `/api/projects/{project_id}/artwork`:

- `GET /` returns the workspace summary.
- `GET|POST /drafts`, `GET|PATCH|DELETE /drafts/{id}` manage drafts.
- `POST /drafts/{id}/generate-image` creates or reuses a durable image job.
- `POST /drafts/{id}/confirm-stale-prompt` is the source-freshness confirmation
  boundary for a later AI-prompt feature; manual prompts are not stale.
- `GET /jobs`, `GET /jobs/{id}` return safe job history.
- `GET /assets`, `GET|DELETE /assets/{id}` manage gallery metadata.
- `GET /assets/{id}/content` serves inline bytes and
  `GET /assets/{id}/download` adds a safe attachment disposition.
- `POST /assets/{id}/apply` updates apply state idempotently.
- `POST /assets/{id}/reuse-as-draft` creates or reuses a provenance-linked
  draft.

List endpoints use opaque `created_at`/`id` cursors. IDs are resolved only
inside the selected project workspace; cross-project IDs and invalid path
components never select another project's bytes.

## Backup and clone expectations

A backup must copy the complete `output/artwork/` tree as one filesystem
snapshot. Restoring only JSON or only `images/` is incomplete; reconciliation
will fail closed or remove unverifiable gallery entries.

Normal project cloning holds an artwork snapshot lock while copying this tree.
Committed assets, drafts, history, and apply state remain self-contained in the
clone. Copied `queued` jobs become `failed` with `cloned_job_not_resumed`, and
copied `running` jobs become `interrupted_unknown`; a clone never replays a
possibly chargeable request. Replanning clones preserve the old workspace only
inside their read-only legacy source-output reference, consistent with the
existing replanning lifecycle.

## Test safety

Automated validation uses fake transports, local `httptest` servers, and fixed
small image fixtures only. It must not call a real gateway or generate a paid
image.
